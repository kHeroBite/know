## 1. 아키텍처 결정

### 1.1 현행 JSP 고도화 vs Python 신규 개발

| 평가 항목 | JSP 고도화 (Tomcat 6 유지) | Python 신규 개발 (FastAPI) |
|-----------|--------------------------|--------------------------|
| **개발 속도** | ❌ Scriptlet 121개 리팩토링 비용 높음 | ✅ 모던 프레임워크로 빠른 개발 |
| **유지보수성** | ❌ Scriptlet 80%가 비즈니스 로직 혼재 | ✅ 명확한 계층 분리 (Router/Service/Repository) |
| **보안** | ❌ SQL Injection 가능, 평문 비밀번호, CSRF 없음 | ✅ 프레임워크 수준 보안 기본 내장 |
| **쉘/펄 통합** | ❌ Java ProcessBuilder로 우회 호출 | ✅ subprocess/asyncio 직접 통합, 펄 14개 즉시 대체 |
| **형태소분석 엔진** | ✅ jiana1.5.jar 네이티브 호출 | ⚠️ subprocess로 JAR 래핑 필요 |
| **기존 DB 호환** | ✅ JDBC 직접 연결 | ✅ SQLAlchemy/PyMySQL로 연결 |
| **인력 현실** | ❌ JSP/Java 6 숙련자 감소 추세 | ✅ Python 인력풀 풍부 |
| **운영 인프라** | ✅ 기존 Tomcat 활용 | ⚠️ Python 런타임 + 프로세스 관리자 신규 설치 |
| **학습 곡선** | ✅ 기존 패턴 유지 | ⚠️ 신규 프레임워크 학습 필요 |

### 1.2 권장안: **Python 신규 개발 (하이브리드 전환)**

**이유:**
1. 현행 JSP는 **기술 부채가 심각** (Tomcat 6 EOL, Scriptlet 방식, 보안 취약)하여 고도화보다 신규 개발이 효율적
2. 핵심 자동화 대상인 쉘/펄 스크립트 14개를 **Python으로 직접 대체** 가능 → 통합 비용 최소화
3. Java 형태소분석 엔진(jiana1.5.jar)은 **subprocess 래핑**으로 유지 → 리스크 최소화
4. TOBE 화면설계서의 파이프라인 자동화 요구사항은 **Python asyncio/Celery**가 최적

**하이브리드 전략:**
- **신규 시스템**: Python FastAPI (프론트엔드 + API + 파이프라인 엔진)
- **유지 컴포넌트**: jiana1.5.jar, dqdic-1.0.3.jar (JAR 래핑), MariaDB (스키마 마이그레이션)
- **폐기 대상**: Tomcat 6, JSP Scriptlet, know_common.jar (Python으로 재구현)

### 2.2 쉘/펄 스크립트 통합 전략

#### A. Python 직접 대체 (14개 스크립트)

```python
# 예시: refine_log_spam.sh → Python 대체
class 검색로그정제기:
    """기존 refine_log_spam.sh 대체"""

    def __init__(self, 스팸패턴경로: str, 상품코드패턴경로: str):
        self.스팸패턴 = self._패턴로드(스팸패턴경로)    # spam_kwd.pat
        self.상품코드패턴 = self._패턴로드(상품코드패턴경로)  # prodcode_pat.cmd

    def 정제(self, 입력파일: Path) -> list[str]:
        """입력 검색로그 → 정제된 키워드 목록"""
        키워드목록 = self._파일읽기(입력파일)
        키워드목록 = self._스팸제거(키워드목록)
        키워드목록 = self._상품코드제거(키워드목록)
        키워드목록 = self._중복제거(키워드목록)
        return 키워드목록
```

#### B. JAR 래핑 (5개 스크립트 → Python subprocess)

```python
class 형태소분석래퍼:
    """jiana1.5.jar를 subprocess로 호출"""

    JAR_경로 = "/opt/know/lib/jiana1.5.jar"
    JDK_경로 = "/usr/lib/jvm/java-1.7.0"

    async def 분석(self, 입력파일: Path, 사전경로: Path) -> Path:
        """cotton_test.sh 대체: 형태소 분석 실행"""
        명령 = [
            f"{self.JDK_경로}/bin/java",
            "-cp", self.JAR_경로,
            "com.diquest.jiana.LiteTest",  # 클래스명 확인 필요
            str(입력파일),
            str(사전경로)
        ]
        프로세스 = await asyncio.create_subprocess_exec(
            *명령,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE
        )
        stdout, stderr = await 프로세스.communicate()

        if 프로세스.returncode != 0:
            raise 형태소분석오류(stderr.decode())

        return self._결과파싱(stdout.decode())


class 사전빌드래퍼:
    """dqdic-1.0.3.jar + ant를 subprocess로 호출"""

    async def 빌드(self, 도메인: str, 소스디렉토리: Path) -> Path:
        """jiana_dic_add.sh 대체: 텍스트 → 바이너리 사전 빌드"""
        # 1단계: ant dic 호출
        결과 = await asyncio.create_subprocess_exec(
            "ant", "dic",
            "-Ddomain", 도메인,
            "-Dsrc.dir", str(소스디렉토리),
            cwd=str(self.빌드디렉토리)
        )
        await 결과.wait()
        return self.빌드디렉토리 / "data" / f"{도메인}.dcd"
```

**래핑 대상:**
| 기존 스크립트 | Python 래퍼 | JAR 의존성 |

| `cotton_test.sh` | `형태소분석래퍼.분석()` | jiana1.5.jar |
| `jiana_test.sh` | `형태소분석래퍼.테스트()` | jiana1.5.jar |
| `jiana_dic_add.sh` | `사전빌드래퍼.빌드()` | dqdic-1.0.3.jar |

| `diffWord.sh` | `사전빌드래퍼.단어비교()` | dqdic-1.0.3.jar |

### 2.3 Celery 파이프라인 설계

```python
from celery import chain, group, chord

# 전체 파이프라인 정의
def 지식작업_파이프라인(도메인: str, 입력파일경로: str, 작업자목록: list):
    """수동 7단계 → 자동 파이프라인"""

    파이프라인 = chain(
        # Stage 1: 데이터 입수 + 전처리
        group(
            검색로그수집.s(도메인),           # CS서버에서 자동 수집
            실패검색어수집.s(도메인),          # 실패 검색어 수집
        ),
        검색로그정제.s(),                     # 스팸/상품코드 제거
        중복제거_및_정렬.s(),                  # 정제 완료

        # Stage 2: 형태소 분석
        형태소분석.s(도메인),                  # jiana1.5.jar 호출
        분석결과변환.s(),                      # 포맷 변환

        # Stage 3: 작업 분배
        작업분할_및_할당.s(작업자목록),         # n등분 + 담당자 할당
        알림발송.s(),                          # 이메일/웹 알림

        # Stage 4: 사전 등록 (반자동 — 승인 후 실행)
        # → 웹 UI에서 작업자가 검토 후 승인 버튼 클릭

        # Stage 5: 사전 빌드 + 배포
        사전빌드.s(도메인),                    # ant dic 호출
        빌드결과검증.s(),                      # 바이너리 검증
        배포.s(도메인),                        # 운영 서버 반영
    )

    return 파이프라인.apply_async()
```

### 3.2 단계별 컴포넌트 상세

| 단계 | 컴포넌트 | 기술 | 입력 | 출력 | 인터페이스 |
|------|---------|------|------|------|-----------|
| **데이터 입수** | `수집기` | Python (paramiko/httpx) | CS서버 로그/DB | 원본 검색로그 (UTF-8) | SFTP/REST API |
| **전처리** | `정제엔진` | Python (re, pandas) | 원본 로그 | 정제된 키워드 목록 | Celery Task |
| **형태소분석** | `분석래퍼` | Python → Java (subprocess) | 정제 키워드 | 형태소 분석 결과 | subprocess (JDK 1.7) |

| **사전빌드** | `빌드래퍼` | Python → Java/Ant (subprocess) | txt_resrc/* | data/*.dcd | subprocess (ant dic) |
| **배포** | `배포관리기` | Python (paramiko/rsync) | *.dcd 바이너리 | 운영 서버 반영 | SSH/rsync |

## 5. 리스크 및 제약사항

### 5.1 know_common.jar 역컴파일 필요성 평가

| 항목 | 필요성 | 이유 |
|------|--------|------|
| **SQL 쿼리 추출** | 🔴 필수 | *DB Handler 7개의 SQL 쿼리가 Python 재구현에 필요. DOMAIN_MNG, ACCOUNT_MNG, {SITE}_UDIC 등의 CRUD SQL을 정확히 파악해야 함 |
| **JianaAdminCommand 프로토콜** | 🔴 필수 | 사전 빌드 명령 프로토콜을 이해해야 dqdic-1.0.3.jar과의 인터페이스 재구현 가능 |
| **ConnectionFactory** | 🟡 참고 | DB 연결 설정 확인 (host, port, charset, pool 크기). MariaDB 직접 연결로 대체 가능 |

**권장 접근:**
1. `jd-gui` 또는 `cfr` 디컴파일러로 know_common.jar 역컴파일
2. SQL 쿼리 + JianaAdminCommand 프로토콜 추출 → 문서화
3. 추출된 SQL을 SQLAlchemy 모델로 변환

### 5.2 Java 형태소분석 엔진 의존성

```yaml
리스크: jiana1.5.jar는 JDK 1.7 필수 — CentOS 7에서만 안정 동작 확인
영향: 서버 OS 업그레이드 시 JDK 1.7 호환성 문제 가능
대응:
  단기: 현행 JDK 1.7 유지 + subprocess 호출 (격리)
  중기: JDK 1.8에서 동작 테스트 → 가능하면 JDK 1.8로 통일
  장기: 형태소분석 엔진 대체 검토 (MeCab-ko, Kiwi 등 Python 네이티브)
  비상: Docker 컨테이너에 JDK 1.7 + jiana 격리 (OS 독립)
```

### 5.3 MariaDB 5.5 호환성

```yaml
리스크:
  - MariaDB 5.5는 2020년 EOL — 보안 패치 없음
  - UTF-8은 3바이트만 지원 (이모지 등 4바이트 문자 불가)
  - JSON 타입 미지원 (10.2+)
  - Window Functions 미지원 (10.2+)

  Phase 1~2: MariaDB 5.5 그대로 사용 (기존 스키마 호환)

    - UTF-8 3바이트 제한 인지하고 코드 방어
  Phase 3: MariaDB 10.6+ 업그레이드
    - mysqldump → 마이그레이션 → UTF-8mb4 전환
    - 업그레이드 전 테스트 DB에서 기존 데이터 호환성 검증
```

### 5.4 기존 25개 도메인 데이터 마이그레이션

리스크:

| 12 | **기존 사용자 교육/전환 계획** | UI 설계 반영 | 이해관계자 인터뷰 |

### 6.3 프론트엔드 기술 선택 (Phase 2 시작 전 결정)

```yaml
옵션_A: React 18 + Ant Design
  장점: 생태계 최대, 관리도구 컴포넌트 풍부, 인력풀 넓음
  단점: 학습 곡선 (JSX, 상태관리)

  장점: 학습 곡선 낮음, 한국 사용자 많음, SFC 직관적

  장점: 프론트엔드 빌드 불필요, Python 단일 스택
  단점: 복잡한 인터랙션 구현 제한, 실시간 업데이트 어려움

권장: 옵션_A 또는 옵션_B (실시간 파이프라인 모니터링에 SPA 필수)
```

-- 파이프라인 실행 이력
CREATE TABLE pipeline_history (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    domain VARCHAR(50) NOT NULL,
    status ENUM('running', 'paused', 'completed', 'failed', 'cancelled') NOT NULL,
    current_stage VARCHAR(20),
    started_at DATETIME NOT NULL,
    completed_at DATETIME,
    started_by INT REFERENCES ACCOUNT_MNG(IDX),
    input_file VARCHAR(500),
    result_summary TEXT,
    error_message TEXT
) ENGINE=InnoDB DEFAULT CHARSET=utf8;

-- 파이프라인 단계별 로그
CREATE TABLE pipeline_stage_log (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    pipeline_id BIGINT REFERENCES pipeline_history(id),
    stage VARCHAR(20) NOT NULL,
    status ENUM('pending', 'running', 'completed', 'failed', 'skipped') NOT NULL,
    started_at DATETIME,
    completed_at DATETIME,
    input_count INT,
    output_count INT,
    log_text TEXT
) ENGINE=InnoDB DEFAULT CHARSET=utf8;

-- 작업 분배/할당
CREATE TABLE task_assignment (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    pipeline_id BIGINT REFERENCES pipeline_history(id),
    assignee_id INT REFERENCES ACCOUNT_MNG(IDX),
    assigned_at DATETIME NOT NULL,
    completed_at DATETIME,
    status ENUM('assigned', 'in_progress', 'completed') NOT NULL,
    item_start INT NOT NULL,
    item_end INT NOT NULL,
    item_count INT NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8;

-- 사전 빌드 이력
CREATE TABLE build_history (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    domain VARCHAR(50) NOT NULL,
    build_type VARCHAR(20) NOT NULL,
    status ENUM('running', 'completed', 'failed') NOT NULL,
    started_at DATETIME NOT NULL,
    completed_at DATETIME,
    started_by INT REFERENCES ACCOUNT_MNG(IDX),
    source_snapshot TEXT,
    output_path VARCHAR(500),
    file_size BIGINT,
    checksum VARCHAR(64),
    log_text TEXT
) ENGINE=InnoDB DEFAULT CHARSET=utf8;

-- 감사 로그
CREATE TABLE audit_log (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id INT REFERENCES ACCOUNT_MNG(IDX),
    action VARCHAR(50) NOT NULL,
    target_type VARCHAR(50),
    target_id VARCHAR(100),
    detail TEXT,
    ip_address VARCHAR(45),
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8;
